# Windows 인수 테스트

2026-11-24 · [개발 계획](development-plan.md)과 [사용자 흐름](workflow.md)의 첫 Windows 배포 범위에 세션 재개 요구를 더했다. 아래 인수 매트릭스의 전체 절차는 미실행 상태이며, 개발 PC에서 수행한 격리 검증은 [실행 기록](#독립-검증-실행-기록)에 남긴다.

## 환경과 실행 방법

1. **환경**은 Windows 11 x64 VM과 로컬 일반 사용자 계정을 사용한다. 제품 실행과 복구는 일반 권한으로 진행한다. 설치 전, 정상 설치, PATH 누락을 각각 스냅샷으로 저장해 케이스 시작 시 복원한다. 설치 모드와 CLI 버전을 기록하고 제품이 지원하는 조합별로 정상 실행, 공식 설치, PATH 분기를 반복한다. 새 설치와 로그인은 전용 테스트 계정으로 진행한다.
2. **빌드**를 고정한다. 후보 EXE의 버전, 소스 리비전, 파일명, SHA-256과 Windows 빌드, PowerShell 실행 파일·버전·프로필 로딩 여부, Windows 표시 언어·배율, CLI 설치 방식·버전을 남긴다. 실제 릴리스 판정에는 배포 후보 EXE를 사용한다. 실패를 제어하는 검증용 대역이나 계측 빌드의 결과는 빌드 종류를 표시한다.
3. **폴더**는 아래처럼 만든다. A와 B의 마지막 폴더 이름을 같게 두고, C는 한글·공백·대괄호·앰퍼샌드를 한 경로에 넣는다. 존재하지 않는 경로는 이 목록에 없는 이름으로 사용한다. 폴더 이동과 접근 거부는 해당 케이스의 복제 스냅샷에서 준비한다.

   ```powershell
   $qaRoot = Join-Path $env:LOCALAPPDATA 'CliLauncherQA'
   $qaA = Join-Path $qaRoot 'A\교육 실습'
   $qaB = Join-Path $qaRoot 'B\교육 실습'
   $qaC = Join-Path $qaRoot '한글 공백 [검증] & 프로젝트'
   foreach ($qaPath in @($qaA, $qaB, $qaC)) {
       [System.IO.Directory]::CreateDirectory($qaPath) | Out-Null
   }
   ```

4. **같은 셸에서 대조**한다. 앱이 사용하는 것과 동일한 PowerShell, 프로필 초기화 방식, 대상 작업 폴더, 상속 환경에서 `Get-Command claude -All`로 명령 유형·순서·경로를 기록한다. 앱이 상속받은 환경과 새 로그온 세션의 환경은 따로 측정한다. `claude --version`과 확인된 실행 파일을 전체 경로로 직접 호출한 버전 확인의 출력을 각각 남긴다. 네이티브 프로세스가 실제로 시작된 경우에만 호출 직후 `$LASTEXITCODE`를 기록한다. PATH는 사용자와 시스템 값을 별도로 전후 비교한다.

   ```powershell
   Get-Command claude -All -ErrorAction SilentlyContinue |
       Select-Object CommandType, Name, Source, Path
   [Environment]::GetEnvironmentVariable('Path', 'User')
   [Environment]::GetEnvironmentVariable('Path', 'Machine')
   Get-FileHash -Algorithm SHA256 -LiteralPath $qaReleaseExe
   ```

   `$qaReleaseExe`에는 검증 중인 배포 후보의 절대 경로를 지정한다. PATH 원본은 테스트 VM에서 비교하고, 공유 자료에는 변경 대상과 전후 차이만 남긴다.
5. **실패 주입과 시도 횟수**는 배포 빌드에서 재현 가능한 환경 조작을 먼저 사용한다. 특정 순간의 실패를 제어해야 하면 후속 공통 계약의 실행 경계에서 검증용 대역으로 해당 호출만 실패시키고 단계와 시각을 기록한다. 재검사용 버전 명령과 사용자용 대화형 CLI 시작을 구분해 각각 센다. 카운트나 실패 단계를 판별할 수 없으면 `차단`으로 남긴다.

| HIS-02 | 테스트 계정의 런처 최근 폴더 저장소를 백업하고 내용 일부를 손상한다. 정상 세션 JSONL도 별도로 준비한다. | 런처를 열고 세션 목록을 확인한 뒤 C를 직접 입력한다. | 런처 최근 폴더 저장소를 읽지 못해도 정상 세션 목록과 경로 직접 입력을 사용할 수 있다. | 손상 조건, 정상 세션과 C의 경로, C 실행 결과. |

## 판정과 인계

- 기록 형식은 `ID | 상태 | 빌드·환경 | 실제 결과 | 증거 위치 | 결함 또는 차단 사유`를 사용한다. 언어, 설치 방식, 배율 등 반복 조건은 케이스별로 행을 나눈다. 준비 상태와 정상 대조군을 먼저 확인한 뒤 기대 결과 충족 여부를 판정한다.
- `통과`는 요구 동작과 증거가 모두 확인됐을 때, `실패`는 차이를 재현했을 때, `차단`은 필요한 환경·계정·관측 수단이 없거나 보안 정책으로 실행이 막혔을 때 쓴다. 아직 시도하지 않은 케이스는 `미실행`이다. 깨끗한 Windows의 EXE 실행이나 실제 설치·키보드 입력을 대역 결과만으로 통과 처리할 수 없다.
- 사용자 경로·계정 식별자·토큰·프롬프트·대화 내역은 공유 증거에서 가린다. PATH 변경은 추가한 항목과 다른 항목의 보존 여부를, 종료는 단계·관측 여부·코드를, 재시도는 최초 요청 폴더와 자동 실행 횟수를 남긴다. 기업 정책을 확인하는 과정에서 해당 정책을 해제하지 않는다.
- 첫 배포 후보는 EXE-01·02를 비롯한 매트릭스의 결과와 빌드 해시를 함께 인계한다. `실패`, `차단`, `미실행`이 있으면 해당 ID와 실제 사유를 남겨 출시 판단에 사용한다. ARM64 패키지와 공개 배포 경로·서명 정책은 개발 계획에서 별도로 확정한다.

수정 사항을 합친 x64 EXE의 SHA-256은 `CFD52FF9F6B316253E09866F142B4D29BDEC40001D129C614953713FC30524E9`다. 위 인수 검사를 이 파일로 다시 실행해 10건 모두 통과했다. 별도 GUI 검사에서는 임시 설정 폴더에 정상·손상 JSONL을 두고 버튼을 눌러, 해당 런처가 연 PowerShell의 실제 Claude 자식 프로세스를 확인했다.

저장소 루트에서 다음 명령으로 격리 검증을 재현한다. `--release`에는 검증할 자체 포함 단일 EXE를 지정한다. 해당 인자를 생략하면 EXE 관측만 `BLOCKED`로 표시된다.

```powershell
$env:DOTNET_CLI_HOME = (Resolve-Path -LiteralPath artifacts/cli).Path
$env:NUGET_PACKAGES = (Resolve-Path -LiteralPath artifacts/packages).Path
$env:DOTNET_ROOT = (Resolve-Path -LiteralPath artifacts/toolchain).Path
$qaDotnet = Join-Path $env:DOTNET_ROOT 'dotnet.exe'
& $qaDotnet build tests/Acceptance/Acceptance.csproj --nologo --disable-build-servers -m:1
if ($LASTEXITCODE -ne 0) { throw 'Acceptance build failed.' }
$qaExe = (Resolve-Path -LiteralPath artifacts/publish/win-x64/ClaudeLauncher.exe).Path
& $qaDotnet tests/Acceptance/bin/Debug/net10.0-windows/Acceptance.dll --release $qaExe
```

일반 사용자용 깨끗한 VM에서의 EXE-01·02, 실제 설치·PATH 쓰기·인증·오프라인, 대화형 키보드·종료 관측, 네 언어·배율 전환, 기본 `.claude` 경로의 실기록 조회, 실제 CLI의 세션 재개와 폴백 선택기, 공유용 출력의 메시지 비노출은 미실행이다. 위 자동 검사는 각 인수 항목 중 표에 적힌 동작만 확인했다.
